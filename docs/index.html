Your database, analyzed by AI

Export your FileMaker database as XML once. The engine reads it. You or an AI agent can then ask questions that used to take hours of manual checking.

🔎

Find bugs automatically

fm-bridge audit crosses every script against the schema. Finds Perform Script calls to deleted scripts, Go to Layout to missing layouts, orphaned table occurrences, ghost fields. A full scan in seconds.

📊

Understand impact before changing

who-calls lists everything that triggers a script — other scripts, layout triggers, buttons. who-uses-field finds every reference to a field across the entire database.

🤖

How to use fm-bridge

For humans with VS Code, and for AI agents over MCP.

📥 Read from FileMaker

Copy script steps in FileMaker (Ctrl+C), then in VS Code:

Ctrl+Shift+P → fm-bridge: Read script from clipboard

✏️ Edit in VS Code

  • Syntax highlighting — steps, variables, strings, comments, numbers
  • Autocomplete — start typing a step name, get snippet templates
  • Diagnostics — red errors (unknown steps) and yellow warnings (missing IDs)
  • Format — inline (matches FM line numbers) or indented (readable)

📤 Write to FileMaker

Ctrl+Shift+P → fm-bridge: Write script to clipboard

Paste in FileMaker's Script Workspace (Ctrl+V).

🔗 Resolve layout IDs

When you write Go to Layout ["SomeName"] without an ID:

Ctrl+Shift+P → fm-bridge: Resolve layout IDs from FMSaveAsXML
→ Pick your database export XML → All IDs auto-filled

🔌 Setup MCP AI

In VS Code, open the Command Palette:

Ctrl+Shift+P → fm-bridge: Set up MCP for an AI agent

Pick your client — Claude Code, Claude Desktop, Cursor, Antigravity, Codex, OpenCode or VS Code itself — and the extension writes the config for you (Codex in TOML, the rest in JSON), merging into what's already there and leaving a .bak. Clients it can see on this machine are marked; the rest fall back to copy-to-clipboard rather than writing somewhere your install never reads. Then restart the client.

It points at ~/.fm-bridge/bin/, not the versioned extension folder, so the config keeps working after an update — and passes FMBRIDGE_CONFIG so the agent finds your live-data connection no matter which directory it was launched from.

Live data, not just structure

FMSaveAsXML exports tell you how the database is built. Some bugs only show up in the rows. fm-bridge reads both — and knows which is which.

🔎

Schema informs the query

Map an XML export to its live database and the engine resolves the right table occurrence, quotes identifiers FileMaker's way, and warns you that a field is an unstored calculation before you spend a query on it.

🔒

Read-only by construction

Statements are accepted by an allowlist parse — one statement, and it must be a SELECT. Not a keyword blocklist, which fails open on /*…*/, string literals and ; chaining.

🧯

Nothing left hanging

Each query runs in a disposable process with a wall-clock kill deadline, one at a time. When it exits the OS closes the socket — an orphaned connection on your server can't happen.

What you need to install

The .vsix already carries the engine and the ODBC sidecar. One thing it cannot carry:

The Claris/FileMaker ODBC client driver.

A free download from Claris, and often already installed by FileMaker Pro or Server. fm-bridge never ships it: it speaks generic ODBC to your system's driver manager (odbc32.dll on Windows, iODBC on macOS, unixODBC on Linux), which loads whatever driver you installed. No third-party redistribution, and nothing to license.

Architecture has to match — the trap that costs everyone an afternoon.

The driver is loaded into the process, so a 64-bit program cannot load a 32-bit driver, and FileMaker Pro on Windows commonly registers only the 32-bit one. The failure is IM002 — data source name not found, which says nothing about bitness. fm-bridge ships both sidecars and falls back automatically, so you never meet this.

On the server, per file:

Enable File ▸ Sharing ▸ ODBC/JDBC, and give the account the fmxdbc extended privilege (File ▸ Manage ▸ Security). That privilege set is the real security boundary — fm-bridge cannot grant itself anything. Use a read-only account.

Missing any of these? Diagnose live data connection names which one and what to do — see DATA.md.

🇪🇸 Para desarrolladores FileMaker en España

FileMaker no te da Veri*FACTU

Si tus clientes facturan desde tu solución, la facturación verificable te toca a ti. Claris no la trae de serie: el encadenamiento de huellas, el XML de la AEAT, el QR y la remisión los escribes tú… o los delegas en una llamada HTTP.

Lo que pide la norma

  • Un registro de facturación por cada factura emitida
  • Huella SHA-256 encadenada con el registro anterior
  • XML conforme al esquema oficial de la AEAT
  • QR en la representación de la factura
  • Remisión al sistema de la Agencia Tributaria

Lo que tendrías que montar

  • Cadena de huellas persistente y a prueba de concurrencia
  • Serialización byte a byte contra el XSD de la AEAT
  • Firma electrónica y gestión del certificado
  • Cliente SOAP, reintentos y control de errores
  • Mantenerlo cada vez que la AEAT cambie el esquema

Lo que hace DataPilotTax

  • Una llamada HTTP desde tu script de FileMaker
  • Devuelve el XML, la huella y el QR listos para guardar
  • La cadena y el histórico los custodia la API
  • Un NIF o cincuenta, con la misma API key
  • También genera Facturae 3.2.1 firmada
